# weport-sync 验证记录

验证日期：2026-10-30（Asia/Shanghai）。
环境：Windows 11、Node v22.22.2、微信 PC（本机账号）、Weport 1.3.0 源码 + 本仓库新增 `export.range`。

## 一、导出命令

新增 `export.range`：单聊天 + 时间窗 + 附件，返回消息数与媒体统计。

| 项目 | 结果 |
|---|---|
| 请求 | 群「宇驰AGENT」（`51992552746@chatroom`），窗口 2026-10-30 00:00 起 24 小时 |
| 结果 | 31 条消息、0 个附件，耗时约 26-30 秒 |
| 请求 | 同上，窗口 2026-10-09 一天（有图片的一天） |
| 结果 | 46 条消息、13 张图片共 1,968,891 字节，`imageKeyMissingFiles=0` |
| 输出结构 | `<批次>/export/群聊_宇驰AGENT/群聊_宇驰AGENT.json` + `media/images/*` |

同时修复了导出服务的两处行为对同步的影响：

1. **媒体目录指纹**：`exportMedia` 打开时，导出服务会遍历 `msg/FileStorage/cache/avatar` 下所有文件做指纹。
   微信附件目录文件量极大，这一步在同步场景会拖到数分钟且无意义（每次都导到全新目录）。
   新增 `skipSourceMediaFingerprint`，仅同步命令启用。
2. **空时间窗**：聊天本身有消息、但窗口内没有消息时，导出服务按失败返回。
   同步命令按"该窗口没有新消息"处理为成功，不产生批次并推进游标。

## 二、端到端（本机 → 本地接收端）

接收端为 `receiver.py`（与本仓库部署的接收服务同一实现），本机 `127.0.0.1:18090`。

| 场景 | 结果 |
|---|---|
| 首次同步（24 小时回看） | 导出 31 条消息 → 打包 5,215 字节 → 上传成功，回执 SHA-256 与本地一致 → 游标推进 |
| 附件批次 | 46 条消息 + 13 张图片 → tar.gz 1,926,060 字节 → 上传成功；包内 17 个条目，中文路径可被 Python `tarfile` 正常读取 |
| 断网 | 停掉接收端后同步：导出 2 条消息成功、上传报 `fetch failed`，批次留在本地（`status=pending`）、游标不动 |
| 恢复补传 | 重启接收端后 `flush`：上传成功 1 包，游标推进到该批次的时间窗末端 |
| 无新消息 | 再跑一轮：识别为空窗口，不产生批次，游标推进，`ok=true` |
| 本地控制台 | `/`、`/api/status`、`/api/log`、`/api/chats?q=` 均返回 200；聊天列表首次 33 秒（751 个会话解析备注名），之后命中缓存 |

## 三、自动化测试

`weport-sync/test/sync.test.mjs`，7 项全部通过：

## 四、边界与未验证项

- 语音、视频附件默认关闭，未用真实样本验证。
- 超过单批上限（默认 10MB）的分卷只做了单元测试，未跑真实大文件。
- 接收端配额与磁盘：测试接收端为 10MB/批、200MB 配额；生产接收端配额需单独评估。
- 客户机部署（`npm install` + `build:dir` 耗时、计划任务权限）未在客户机复跑。
- 同一台机器上不要同时用同一个 `profile` 目录跑两个引擎；同步默认使用独立 profile。
- 引擎被强杀可能残留 `electron.exe` 进程，需手工结束；正常退出路径会关闭引擎。
